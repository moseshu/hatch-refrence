# Hatch 独立证据验证层开发计划

更新日期：2026-11-18。代码审计基线：`e7e06fb`。本文保留完整目标；首批实现和服务器验证说明见 [VERIFICATION.md](../VERIFICATION.md)。本地未编译、未运行 Rust 测试。自动修复编排、通用浏览器检查器、完整租约绑定及固定评估集仍待后续扩展，不能将框架接线视为全部验收完成。

## 1. 目标与范围

把“任务完成”从工作者的自述，变成基于固定验收标准和可追溯证据的系统判断。工具成功返回、模型停止调用工具、审批动作执行成功，都不能单独作为业务目标完成的证明。

首版覆盖文件写入、日历事件创建和邀请任务；随后接入通用 agent 的行动型任务和语义交付。复用现有计划、任务账本、审批服务、失败分类与连接器，避免另建一套任务调度器。

核心交付：

1. 所有受支持任务通过统一完成门槛，普通执行和审批恢复没有旁路。
2. 校验者根据目标、验收契约和独立观察裁决，不依赖工作者推理轨迹。
3. 执行、取证、裁决分别持久化，进程重启后只补齐缺失阶段。
4. 校验失败后的恢复不会重复发送邮件、创建事件等副作用。
5. 以已知失败和正确对照样本评价验证器，持续管理误放行与误拦截。

## 3. 设计原则

### 3.1 验收标准先固定

保留 `expected` 作为人可读说明，增加结构化 `VerificationSpec`。步骤执行前固定契约与规则版本；工作者不能在失败后降低标准，再让同一次执行通过。

契约至少描述：目标资源、必须成立的条件、证据来源、检查器、证据有效期、适用范围。目标、工具参数、验收契约应进行一致性校验；不能完全信任工作者生成的 rubric，避免“要求 A、执行 B、按 B 打分”。

修改目标或契约必须推进计划版本，按现有授权规则决定是否重新审批。规则更新只影响后续版本，不追溯改判已固定的运行。

### 3.2 独立取证优先于增加模型

先用确定性检查器查询真实状态，再对无法确定性判断的语义条件使用 grader。允许同一模型承担 grader，但采用独立上下文、受限读取工具和单独预算。

校验输入只包含用户目标、固定契约、候选产物、目标资源标识、证据及必要执行元数据。工作者输出只作为待验证主张，不作为事实来源。修复轮次可携带先前的验证报告和事实，避免反复从零检查；不传工作者的推理轨迹。

### 3.3 完成与回答分开

`Answered` 保持“产生了回答”的语义，不自动升级为“目标已完成”。行动型任务必须有任务级验收；普通解释、闲聊等无外部交付的回答明确标记 `not_applicable` 及原因。

不对每个探索性工具调用启动一次模型。验证放在有验收条件的交付步骤、不可逆副作用之后，以及任务宣告完成之前。

## 4. 验证协议与数据模型

类型名称为设计草案，最终以仓库依赖边界为准。

| 对象 | 建议字段与职责 |
| --- | --- |
| `VerificationSpec` | schema 版本、契约摘要、规则版本、条件列表、证据新鲜度、检查器标识、步骤或任务作用域 |
| `VerificationSubject` | task/plan/step、计划版本、执行 attempt、动作幂等键、账户和目标资源、产物摘要 |
| `EvidenceRecord` | 来源类型、资源标识、观察时间、资源版本或摘要、受控存储引用、读取错误；区分工具回执与独立回读 |
| `CheckResult` | condition ID、Pass/Fail/Ambiguous、观察值、预期值、证据引用、结构化原因码 |
| `VerificationReport` | subject、spec 摘要、检查结果、总裁决、检查器版本、开始结束时间、成本和恢复建议 |

现有 `StepVerify` 可作为兼容适配层。新服务提供显式的证据读取能力、取消信号和超时，不再只对输出字符串做判断。保持当前同步执行模型，首版不为验证层引入新的异步运行时。

裁决语义：

- **Pass**：所有必需条件均有足够证据成立。
- **Fail**：有充分证据证明至少一个必需条件不成立。
- **Ambiguous**：证据不足、冲突、过期或检查器无法可靠裁决，且没有足以确定失败的证据。报告必须保留全部条件的结果，不能丢掉未确定项。

裁决与副作用状态分开保存：`confirmed_applied / confirmed_not_applied / unknown`。例如事件存在但时间错误属于 Fail + confirmed_applied，不能把它当作“创建没有发生”。未执行检查不属于 Pass，另记 `pending/not_applicable/legacy_unverified` 等覆盖状态。

完成资格还须绑定当前 task/plan 版本与执行 attempt。旧版本报告、修改前文件摘要或已取消任务的迟到结果，不能提交当前完成状态。

## 5. 执行与恢复生命周期

统一逻辑：

```text
固定目标、契约、规则版本
  → 执行并保存动作结果
  → executed_unverified
  → 独立取证与检查
  → 保存 VerificationReport
  → Pass：步骤 Done
    Fail：按副作用状态选择修复、重规划或停止
    Ambiguous：有限次只读对账；仍不明则 NeedsHuman
  → 所有步骤结束后做任务级一致性验收
  → 验收通过才能声明任务完成
```

`executed_unverified` 是逻辑阶段，实施时可用独立验证记录表达，避免无必要地扩展所有既有状态枚举。关键是动作成功与步骤完成之间必须有持久边界。

必须统一以下路径：直接执行、审批后恢复、已执行审批回执重放、worker 重启、常驻任务续跑。审批服务负责授权动作与记录执行事实；统一完成门槛负责业务验收，CLI 和 HTTP 不各自实现一套规则。

崩溃恢复要求：

1. 动作已保存、验证尚未开始：只执行取证。
2. 证据已保存、报告未保存：按有效期复用证据或重新读取。
3. 报告已保存、步骤尚未 Done：幂等提交状态，不重做动作。
4. 外部动作可能成功、本地回执未保存：先对账；无法确认则阻塞。
5. 旧报告遇到新计划版本、资源变化或租约失效：拒绝迟到提交，保留审计记录。

任务级报告须绑定所覆盖的步骤报告、资源版本和契约摘要；修复修改了产物后，相关步骤及任务级旧结论失效。验证不是对外部世界永久不变的保证，报告应明确观察时间与验证范围。

## 6. 首批检查器

| 场景 | 独立证据与检查 | 不足时如何处理 |
| --- | --- | --- |
| 文件写入 | 从受限工作区重新读取目标文件；比较内容摘要、JSON schema 或要求的关键字段 | 路径不符、结构不符为 Fail；读取失败为 Ambiguous，不能因为写工具返回成功而通过 |
| 日历创建 | 用实际账户、calendar ID、event ID 调用查询；比较标题、起止时间、时区、参与人和事件状态 | 短暂查询不到先有限对账；超过一致性窗口仍无可靠证据则 Ambiguous；已确认字段错误为 Fail |
| 邮件发送 | 使用供应商消息 ID 或已发送记录；核对发件账户、收件人和关联事件 | 仅有 `sent ` 文本不够；只证明供应商接受发送，不宣称对方收到或已阅读 |
| 浏览器修改 | 依据任务目标重新打开或查询目标记录，检查关键业务字段 | URL 仅作定位；列头点击、导航成功不能证明记录已修改 |
| 邀请任务整体 | 核对事件、邀请正文、收件人与时区的一致性，关联相应资源 ID | 单步均通过但邀请内容与事件不一致时，任务级 Fail |
| 语义产物 | 根据固定条目核对来源、关键事实、覆盖范围和相互矛盾；事实尽量由独立读取支撑 | 模型无依据的判断不能升级成 Pass；输出条件级理由与证据引用 |

首版不承诺覆盖任意网页和任意供应商。无法提供独立读取能力的操作必须显式呈现验证缺口，并按模式决定观察或阻塞。

文件读取沿用工作区边界；远端回读沿用连接器账户与权限。grader 默认只读，禁止发送邮件、修改文件或扩大权限。外部页面、文件、邮件中的指令都视为不可信内容，不能改写验收规则。

## 7. 失败恢复与预算

| 情况 | 恢复动作 | 是否可以重做副作用 |
| --- | --- | --- |
| 取证超时、限流 | 重试读取，保留原动作结果 | 否 |
| 已确认动作未发生，且故障暂时 | 通过原授权与幂等协议重试动作 | 条件满足时可以 |
| 动作发生但交付不符合标准 | 生成修复或局部重规划；涉及新授权时重新审批 | 不直接重复原动作 |
| 外部状态不明 | 只读对账；仍不明则 NeedsHuman | 否 |
| 无权限、规则缺失、检查器故障 | 记录具体缺口，阻塞或按观察模式报告 | 否 |

建议默认预算：取证首次失败后最多重试 2 次；可自动修复的任务首次验证失败后最多修复 2 轮，即总计最多 3 次验证轮次。取证重试与修复轮次分别计数，跨进程重启不清零。另设总时长、模型调用与费用上限，任一耗尽均诚实停止。

这些是待实现、可配置的默认值，不是对当前所有入口行为的描述。继续复用 `FailureKind` 路由，但新增结构化原因码与安全重试判定，避免根据“timeout”文本重做已生效动作。

## 8. 规则管理与验证器评估

增加仓库级 `VERIFICATION.md`，解释规则约束、取证方式与维护流程；机器规则放在 `verification/rules/`。规则至少包含稳定 ID、适用操作和资源类型、触发条件、检查器、必需条件、失败案例和版本。

产品运行按结构化动作与受影响资源触发规则；Hatch 自身代码评审才按 diff 触发。不要把运行时验证简化为分析自然语言 diff。

任务固定已发布规则集摘要。运行中的工作者和 grader 均无权修改它。新失败先形成候选规则，附可复现案例、正确对照和适用边界，经维护者评审后发布。操作技巧与验收规则分别维护，定期删除重复、过时、高误报条目。

评估集至少包含：伪成功工具输出、错误账户、错误时区、事件重复、写入错路径、跨步骤不一致、回读超时、最终一致性延迟、审批恢复绕过、崩溃恢复、旧版本报告、grader 被产物指令干扰，以及正确任务对照。规则调优集与固定评估集分开。

指标分别统计：不合格结果被判 Pass 的比例、正确结果被判 Fail 的比例、Ambiguous 比例、验证覆盖率、修复成功率、人工介入率、重复副作用数、验证延迟与成本。另比较独立取证后发现的问题及最终裁决，识别 grader 是否丢掉已找到的失败。不能只看任务最终成功率。

用户提到的 WorkArena“复读轨迹救回 0 道”作为待导入实验线索；本文未审计其原始结果，不将它作为已验证基线。后续比较无验证、轨迹自查、独立确定性回读、独立回读加 grader，记录相同任务与模型配置。

## 9. 实施工单与交付顺序

| 阶段 | 工单与主要落点 | 阶段验收 |
| --- | --- | --- |
| P0-A 完成门槛 | 审计所有完成入口；在 `hatch-plan` 统一直接执行和审批恢复的结算；将未验证与 Done 分开；增加配置模式 | 受支持步骤缺报告不能完成；审批恢复走相同检查；无检查器不会隐式 Pass |
| P0-B 持久协议 | `hatch-store` 迁移与验证表；`hatch-plan` 契约、报告、版本校验；`hatch-tasks` 关联和事件；统一幂等提交 | 契约不可随当前执行自改；重启不重做动作；旧版本和失效租约报告不能提交 |
| P0-C 独立回读 | 文件检查器；日历连接器查询与检查器；邀请流替换文本检查；`task_plan_runner` 和计划 CLI 接入 | 伪成功返回、错误文件、错误事件字段被拦下；真实读取正确结果可通过 |
| P1-A 恢复闭环 | 结构化失败与副作用状态；读取重试、修复、重规划预算；审批服务及 worker 对账 | 超时不重复创建或发送；最多 2 轮修复；未知状态阻塞并说明原因 |
| P1-B 核心循环与任务验收 | `hatch-agent` 增加候选完成检查点；行动型任务调用验证服务；只对已验证答案发完成事件；邀请流整体检查 | 模型说“完成”不能绕过门槛；单步成功但整体不一致不能完成；普通问答保持可用 |
| P1-C 可观测与呈现 | 任务详情/API/SSE 展示验证状态、证据摘要、原因和下一步；凭据和邮件内容受控存储 | CLI 与 API 对同一任务呈现一致；能区分已执行待验证、验证失败、状态不明 |
| P2-A 语义 grader | 独立上下文、受限读取、条件级结构化输出、预算与降级；通过 trait 注入，避免 plan 与 agent 循环依赖 | 事实不足不会判 Pass；grader 故障可恢复；评估显示有收益后才扩大使用 |
| P2-B 规则迭代 | 规则注册、候选规则、回归样例、固定评估与维护流程 | 新规则不能改变当前运行的标准；每条启用规则有正反例和维护记录 |

依赖：P0-A 与 P0-B 共同构成可上线门槛，不能只合并回调接线就宣布完成。P0-C 依赖二者；P1-A、P1-B 基于完整持久协议接入；P1-C 在 enforce 上线前交付；P2 不阻塞确定性检查器上线。

首个可交付切片限定为“文件写入 + 计划直接执行/审批恢复 + 持久报告 + 崩溃恢复”，随后扩到真实日历，再处理邮件回读与语义判断。每个切片都须闭合执行、验证、恢复和用户呈现。

## 10. 测试与发布

必要测试按风险选取，不为每个结构体复制实现细节：

1. 计划集成测试：直接执行、审批恢复、缺失检查器、契约变更和任务级失败。
2. 故障注入：动作完成后、证据保存后、报告提交前后崩溃；重复恢复和并发领取。
3. 连接器契约测试：正确/错误字段、供应商接受但回读延迟、查询超时、账户不匹配；CI 使用 fixture。
4. 不变量测试：未知副作用不得自动重放；旧报告不得完成新版本；报告重复提交不产生重复完成事件；重启不重置预算。
5. 独立评估：已知失败与正确对照都要运行；受控真实账户试点单独记录，不将 mock 通过称为端到端通过。

上线模式：`off / observe / enforce`。observe 保留现有完成行为并单独记录“若强制会怎样”，不能把影子结果显示成“已验证”；enforce 中，受支持的行动型任务没有有效 Pass 就不能成功。按任务类型和规则版本灰度，不一次覆盖全部入口。

首版发布硬门槛：上述安全不变量全部通过；固定负例没有错误放行；正确对照没有意外拦截；重复副作用为零；恢复预算不因重启失效；用户能看到未通过原因。真实试点同时报告样本量、覆盖范围与成本，有限样本零失败不宣称普遍零风险。扩大灰度前由维护者确定试点的延迟、成本、误报和介入率阈值。

回滚可将规则或任务类型降为 observe 并保留历史报告；不撤销已确认的外部动作，不自动重放未确定动作。正在执行的任务保持固定规则版本与明确迁移策略，不能因全局开关切换而悄悄改变验收口径。

旧记录不批量标记为已验证，也不重做副作用；记录为 `legacy_unverified`。旧的未完成任务在下一次有副作用的执行前补齐契约，无法无损迁移时保留现场并请求必要信息。

## 11. 完成定义

该计划完成意味着：文件、日历和邀请任务具备固定契约、独立证据、步骤与任务级裁决；直接执行、审批、重启和核心 agent 均遵守同一完成资格；失败能安全恢复或诚实停止；用户与评估系统能够复查完成结论的依据。仅增加提示词、回调或第二模型调用不算完成。
