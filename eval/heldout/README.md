# 留出集（held-out）

开发集是改代码时一直对着看的任务，比如 `eval/worlds/` 下的评估世界。一个改动在开发集上通过了，有可能只是适应了这几道题。留出集用来回答它是不是真的变好了：任务由**没读过实现的人**来写，**不进仓库**，改代码的人只看**汇总数字**。

目前支持记忆类评估（和 `memory-crossday`、`memory-pressure` 格式相同）。

## 怎么写

1. 把 [`template/`](template/) 复制到**仓库之外**的目录，比如服务器上的 `~/hatch-heldout/recall-v1/`。放在仓库里（包括被 git 忽略的目录）会被直接拒绝，因为改代码的会话能读到。
2. 按下面的格式改 `memory.json`，需要的工作区文件放进 `project/`。
3. 自己写，不要参考 `eval/worlds/` 里的任务，也不要去看召回的实现。运行前会检查有没有复用仓库世界里的数据。

### memory.json 的字段

和记忆评估世界一样（见 `eval/worlds/memory-pressure/README.md`），留出集额外要求：

| 字段 | 要求 |
|---|---|
| `seed_claims[].at` | 带 `tags` 的记忆时间互不相同（固定注入按创建时间取最早 12 条，时间相同会让顺序不确定） |
| `seed_claims[].key` | 目标记忆要有 `key`，供 `targets` 引用 |
| `targets[].category` | 必填，见下表 |
| `targets[].checks` | 必填，列出判定这个目标的任务结果的检查名称 |
| `checks` | 只看结果（草稿收件人、正文、日程时间地点、写出的文件），不看措辞 |

`category` 描述请求和它需要的记忆之间的关系，汇总按它统计。判断标准是**检索系统看到的词**，不是语义：把记忆的"主题 + 内容 + 标签"和会话的**第一条**用户消息分别切成索引词，看共有多少个"词"。这里的词指英文单词、数字和编号，以及相邻两个汉字；单个汉字不算，它们在排序里权重很低。

只看第一条消息，是因为每轮召回只用那一轮的输入，汇总统计的也是首个请求。编号如果到第二轮才补上，这个目标按第一条消息算就不是 `literal`。

| 值 | 定义（按共有的词） | 例子 |
|---|---|---|
| `lexical` | 至少共有 1 个词 | 请求"回复供应商邮件"，记忆"回复供应商邮件时……" |
| `literal` | 原文里共有一个完整标识：字母和数字组成的编号、代码，或邮箱地址 | 请求提到合同 HT-1234，记忆写着它的对接人 |
| `paraphrase` | 意思相同，没有共有的词，最多零星单字 | 请求"找个开会的地方"，记忆"订会议室优先选……" |
| `unmentioned` | 请求不涉及记忆的话题，没有共有的词，最多零星单字 | 请求"挑家餐厅"，记忆"对花生过敏" |
| `other` | 以上都不是 | |

注意"完全没提"很容易写偏：请求和记忆提到同一个人名、同一个项目名，按检索算就已经是词面交集了。

`literal` 按完整标识比对，不按索引词：切词会把 HT-2291 拆成 ht 和 2291，请求写 PO-2291 时也会共有 2291。只有数字的串（年份、金额、分机号）不算标识。

### 运行前的目标校验

每次运行记忆类评估（不只是留出集）都会先按上面的定义检查每个目标，不符合时在终端打印警告，然后继续运行：

- 标签和实测不符，比如标成"完全没提"却和请求共有 3 个词；
- 目标落在固定注入里：它带标签，而且是最早的 12 条带标签记忆之一，每轮都会注入，测不到召回。要测召回，把它的时间改晚或去掉标签。

警告只写目标的序号和类别，不含内容，留出集也可以放心看。

### 检查里可以用的字段

| 类型 | 字段 |
|---|---|
| `email_draft` | `to_includes` 必须包含、`to_excludes` 不能包含、`to_exact` 收件人必须恰好是这些（不需要就省略，写空列表会在加载时报错） |
| `email_body` | `includes`、`excludes`、`last_line` |
| `event_draft` | `local_start`、`local_end`（可选）、`location_includes` |
| `file_names` | `path`、`allowed`、`forbidden`、`min_allowed` |

### 建议的规模

- 每个 `category` 至少 3 个目标，否则一次波动就决定结论。
- 预置记忆要多：带标签的偏好超过 12 条，让固定注入装不下；再加一批和请求有共同词的普通记忆参与排名竞争。
- 人名、邮箱、编号都用新的，不要和仓库世界重复（人设 Alex / `alex@corp.example` 除外）。

## 怎么跑

```bash
hatch eval --world ~/hatch-heldout/recall-v1 --live --heldout --recall auto --out ~/hatch-heldout/runs/recall-v1-auto
```

运行前会先做独立性检查，发现下列问题就直接退出，不调用模型：
- 目录在仓库里；
- 目标缺 `category` 或 `checks`；
- 和仓库世界共用了邮箱或编号；
- 有记忆或请求和仓库世界一字不差。

终端（以及 `--out` 下的 `summary.md`）只显示汇总：通过数、各类别的目标在首个请求里是固定注入还是自动召回拿到的、有没有被工具找到、任务检查是否通过，以及成本（搜索、提问、步数、token）。不显示检查名、会话、请求、记忆内容和回答。

**只把汇总交给改代码的人。** `--out` 目录里还有完整报告和诊断轨迹，这些留在私有目录里，用来自己排查。

## 每次运行留下什么

所有记忆类评估只要给了 `--out`，都会写出这些（不只是留出集）：

| 文件 | 内容 |
|---|---|
| `report.json`、`report.md` | 完整报告 |
| `run.json` | 运行清单：提交号和有没有未提交的改动、模型、召回方式、fixture 指纹（世界目录的 SHA-256）、开始和结束时间、通过数、用量 |
| `traces/NN-<会话>.json` | 逐轮记录：输入、每次模型请求的上下文摘要号、每个工具调用的参数和结果、回答 |
| `contexts/<摘要号>.txt` | 模型实际收到的系统上下文，相同的只存一份 |
| `summary.md` | 只有留出集运行才写：可以外传的汇总 |

写出前都经过密钥脱敏。

## 用完之后

留出集一旦被用来指导改代码（比如有人看了它的详细报告再去调提示词），就不再是留出集了，下一轮验收要换一份新写的。
